_libmdbx_ — встраиваемая транзакционная [key-value база данных](https://ru.wikipedia.org/wiki/Модель_«ключ—значение»)
с [лицензией Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0): компактная,
чрезвычайно быстрая, ориентированная на создание лёгких надёжных решений.

1. Позволяет **рою многопоточных процессов ACID-но читать и обновлять** несколько
   key-value [таблиц](https://ru.wikipedia.org/wiki/Ассоциативный_массив) и
   [мультитаблиц](https://ru.wikipedia.org/wiki/Мультимапа) в локально-разделяемой БД.

2. Обеспечивает **экстраординарную производительность** и минимальные накладные
   расходы через [memory-mapping](https://ru.wikipedia.org/wiki/Отображение_файла_в_память)
   и стоимость `O(log N)` операций благодаря [B+tree](https://ru.wikipedia.org/wiki/B%2B-дерево).

3. **Не требует обслуживания и восстановления после сбоев** — WAL не используется;
   это может быть нюансом для write-intensive нагрузок с требованиями долговечности
   (см. [режимы долговечности](../getting-started/durability-modes.md)).

4. Гарантирует [сериализуемость](https://ru.wikipedia.org/wiki/Сериализуемость) писателей
   через единственный мьютекс и даёт
   [wait-free](https://ru.wikipedia.org/wiki/Неблокирующая_синхронизация) чтение
   параллельным читателям, при этом **чтение и запись не блокируют друг друга**.

5. **Гарантирует целостность данных после сбоя**, если это явно не принесено в жертву
   скорости записи ([режимы долговечности](../getting-started/durability-modes.md)).

6. Поддерживает Linux, Windows, MacOS, HarmonyOS, Android, iOS, FreeBSD, Solaris,
   NetBSD, OpenBSD и другие системы, совместимые с **POSIX.1-2008**.

7. **Компактен и дружелюбен к встраиванию** — несколько плоских файлов исходников,
   без внутренних потоков и серверных процессов; ядро API в духе Berkeley DB
   с большим набором расширений.

Исторически _libmdbx_ — глубоко переработанный потомок легендарной
[LMDB](https://ru.wikipedia.org/wiki/Lightning_Memory-Mapped_Database): наследует её
достоинства, исправляет ряд проблем и добавляет [большой набор доработок](../deep-dive/improvements.md).

## Ключевые возможности

- Key-value модель данных, ключи всегда отсортированы; диапазонные запросы
  с оценкой объёма результата.
- Полный [ACID](https://ru.wikipedia.org/wiki/ACID) через
  [MVCC](https://ru.wikipedia.org/wiki/MVCC) и [copy-on-write](https://ru.wikipedia.org/wiki/Копирование_при_записи).
- Несколько таблиц внутри одного файла БД; эффективная поддержка мультимап
  (dupsort): значения отсортированы и итерируемы, ключи без дублирования.
- Данные memory-mapped и доступны напрямую (zero-copy): полный скан записей
  чрезвычайно быстр; `get(key)` ускоряется разделяемым lock-free кэшем.
- Чтение масштабируется линейно по CPU; транзакции читателей и писателей
  не блокируют друг друга; нет конфликтов и дедлоков (запись сериализована).
- Онлайн-резервное копирование; append-операция для bulk-вставки предсортированных данных.
- Автоматическое изменение размера БД на лету; непрерывная zero-overhead
  компактация; явная дефрагментация.
- Настраиваемый размер страницы; вложенные транзакции; отсутствие WAL и
  журнала транзакций — обслуживание не требуется.

## Ограничения (кратко) { #ограничения-кратко }

Полный разбор — в [Ограничениях и подводных камнях](restrictions.md).

| Параметр | Значение |
| --- | --- |
| Размер страницы | степень двойки: `256`…`65536`, по умолчанию `4096` |
| Размер ключа | до ≈½ страницы (`2022` байт при 4K, `32742` при 64K); поддержка нулевой длины |
| Размер значения | до `0x7FF00000` байт для таблиц; ≈½ страницы для мультимап |
| Размер write-транзакции | до `4.94` ТиБ (4K-страницы), `79.1` ТиБ (64K) |
| Размер БД | до ≈`8.0` ТиБ (4K), ≈`128.0` ТиБ (64K) |
| Максимум таблиц | `32765` |
| Писатели | не более одной write-транзакции одновременно |

## Подводные камни (кратко)

- **B+tree** → доступ к страницам в основном случайный: SSD дают существенный
  выигрыш на больших БД.
- **Shadow paging вместо WAL** → синхронизация может стать узким местом
  write-intensive нагрузок.
- **MVCC + долгие читатели**: параллельная активная модификация данных при
  долгоживущем read-транзакции увеличивает рабочий набор и может исчерпать
  свободное место. Избегайте долгих чтений; используйте
  [парковку транзакций](https://libmdbx.dqdkfa.ru/docs/en/reference/api/group__c__transactions.html)
  и [Handle-Slow-Readers](https://libmdbx.dqdkfa.ru/docs/en/reference/api/group__c__err.html) —
  подробнее в [ограничениях](restrictions.md).
- Чрезвычайная скорость требует внимательности: линейный поиск может оказаться
  выгоднее сложных индексов, а неоптимальность кода заметна только на больших данных.

## Сравнение с другими БД

_libmdbx_ превосходит легендарную _LMDB_ по возможностям и надёжности, не уступая
в производительности (детальный каталог — [Improvements](../deep-dive/improvements.md)).
Кратко по сравнению с классом встраиваемых хранилищ:

- БД разделяется несколькими процессами без мультипроцессных проблем;
- нет проблем с перемещением курсоров после удаления;
- zero-overhead компактация: файл БД может усекаться;
- без учёта дискового I/O — до ≈3× быстрее BoltDB и вплоть до 10–100 000× быстрее
  BoltDB/LMDB в специальных случаях (воспроизводится [ioArena](https://sourcecraft.dev/dqdkfa/ioarena),
  `make bench-quartet`, включая сравнение с RocksDB и WiredTiger);
- функционально богаче BoltDB и/или LMDB.

## Когда выбирать libmdbx

✅ Подходит: локальное встраиваемое хранилище с ACID-гарантиями; много читателей
и умеренная запись; требования zero-maintenance и crash-safety «из коробки»;
кросс-процессный доступ в пределах одной машины; огромные мультимапы и диапазонные
запросы.

⚠️ Подумайте дважды: сетевое/распределённое использование (libmdbx — не сетевая
БД); write-intensive нагрузки с жёсткими требованиями долговечности на медленных
носителях (узкое место — fsync, см. [режимы долговечности](../getting-started/durability-modes.md));
долгоживущие read-транзакции при активной записи (см. [ограничения](restrictions.md)).
